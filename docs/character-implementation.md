# キャラクター実装ガイド

更新日：2026-09-14。現在のGoサーバーとReactフロントの実装をもとにした開発者向け資料です。

## 1. 仕様の参照元

キャラクターの数値・技・パッシブは [rules.md](../specification/rules.md) を基準にします。
状態異常の共通定義など、rulesにない事項は [details.md](../specification/details.md) を確認します。
過去の `characters.md` や別資料の一覧に異なる数値が残っていても、rulesの値を優先します。

このガイドは実装手順を説明する資料です。全キャラクターの数値表を複製して管理する用途には使いません。
仕様内で対象・持続時間・発動順序などが決まっていない場合は、判断した内容をプランナーに報告してください。
特に「1ターン」が双方の手番交代を指すのか、自分の次の手番までを指すのかは確認が必要です。

## 2. 全体構成と変更するファイル

戦闘の正しい状態はサーバーが管理します。フロントはサーバーから定義と試合状態を取得し、表示・入力を担当します。
フロントだけにHP計算や回数制限を追加しても、APIからの操作を制限できません。

| ファイル | 役割 |
| --- | --- |
| [characters.go](../../Auxilia-webserver/internal/game/characters.go) | 基礎能力、攻撃定義、パッシブ名・説明・数値 |
| [engine.go](../../Auxilia-webserver/internal/game/engine.go) | 試合状態、移動・攻撃、ターン切り替え、勝敗・復活 |
| [effects.go](../../Auxilia-webserver/internal/game/effects.go) | 状態異常、ダメージ補正、範囲パッシブ、設置マス、ターン終了処理 |
| [knockback.go](../../Auxilia-webserver/internal/game/knockback.go) | 攻撃方向への押し戻し |
| [handlers.go](../../Auxilia-webserver/handlers.go) | キャラクターAPI、選択の検証、認証済み操作の受付 |
| [store.go](../../Auxilia-webserver/internal/store/store.go) | 試合状態の保存、トランザクション、重複コマンド防止 |
| [types.ts](../lib/types.ts) | APIに対応するTypeScript型 |
| [game.ts](../lib/game.ts) | 状態ごとの技定義選択、状態異常の表示説明、方向キー |
| [page.tsx](../app/page.tsx) | API通信、操作中キャラ・技・方向・試合状態の管理 |
| [entrance-scene.tsx](../components/scenes/entrance-scene.tsx) | 編成、キャラクター選択、並び順 |
| [battle-scene.tsx](../components/scenes/battle-scene.tsx) | 戦闘画面、対象判定、技・パッシブ・現在の状態の表示 |
| [character-image.tsx](../components/character-image.tsx) | 立ち絵・ミニ画像の読み込みとunknownへの切り替え |

基本的な流れは次のとおりです。

1. サーバーの `Definitions` がキャラクター定義を保持する。
2. `GET /api/characters` が定義に使用数・編成総数を付けて返す。
3. フロントが一覧と詳細画面を組み立てる。
4. 試合生成時に定義から各陣営の `Character` を生成する。
5. クライアントがキャラクターID・攻撃番号・方向・対象マスを送る。
6. サーバーが権限・手番・コスト等を検証し、効果を適用して試合状態を保存する。
7. フロントが返された状態で表示を更新する。

## 3. 新キャラクターを追加する手順

### 3.1 実装前に整理する内容

- 一意な英字ID、表示名、立ち絵とミニ画像のファイル名。
- HP、移動コスト、移動可能距離。
- 3つの技それぞれのコスト、ダメージまたは回復量、対象、範囲。
- 状態異常の種類・確率、設置マス、解除効果。
- 自分を対象に含むか、敵味方両方か、拠点にも適用するか。
- 1ターンの回数制限、効果の終了時点、次ターンへの予約効果。
- パッシブの発動条件、対象、範囲、持続時間、使用済み状態。
- 特殊状態で技が変わる場合、その状態遷移。

`MoveCost` と `MoveRange` は異なります。仕様に移動コストしか書かれていない場合、移動距離まで同じ値にしてはいけません。

### 3.2 Definitionsに登録する

`characters.go` の `Definitions` に `CharacterDefinition` を追加します。
次は構造を示す架空キャラの例です。数値は実際の仕様から転記してください。

```go
{
    ID: "example",
    Name: "サンプル",
    Image: "example_mini.png",
    Portrait: "example.png",
    MaxHP: 150,
    MoveCost: 10,
    MoveRange: 1,
    Attacks: [3]AttackDefinition{
        atk("攻撃", 10, 20, "enemy", adjacent),
        atk("回復", 15, -40, "ally", p(Position{0, 0})),
        func() AttackDefinition {
            a := atk("解除", 20, 0, "ally", p(Position{0, 0}))
            a.ClearDebuffs = true
            return a
        }(),
    },
},
```

`ID` はAPI・保存済み試合・使用率集計のキーになります。表示名を変える場合も、既存IDを安易に変更しないでください。
英字表記はrules.mdに従い、内部IDは小文字に統一します。旧IDの `wellbulus`・`shincho` は `CanonicalCharacterID` で `verbulus`・`shicho` に読み替え、保存済み編成・試合・使用率の互換性を維持します。

定義を追加すれば、通常は `GET /api/characters` と選択一覧にも自動で追加されます。
フロントに別の固定キャラクター配列を作る必要はありません。
選択APIは存在するID・3体・重複なしを検証します。

### 3.3 パッシブ説明を登録する

`passiveDefinitions` にIDをキーとして登録します。

```go
"example": {"パッシブ名", "発動条件と対象を含めた説明。"},
```

`init()` がこの内容を各定義の `PassiveName` と `PassiveDescription` に設定します。
説明を追加するだけでは効果は発動しません。処理または `passiveValues` の追加も必要です。

## 4. 攻撃定義の読み方

| フィールド | 意味・注意 |
| --- | --- |
| `Name` | 技名。現在は回数制限の使用履歴キーにもなる |
| `Cost` | 基本消費コスト。状態異常による増減前の値 |
| `Power` | 正数はダメージ、負数は回復、0は直接ダメージなし |
| `Target` | `enemy`、`ally`、`any`、`cell` |
| `Pattern` | 自分を原点とした効果範囲 |
| `Range` | `atk()` がPatternのマンハッタン距離の最大値から算出する補助値 |
| `Effect` / `EffectChance` | 追加する状態異常名／0〜100の確率 |
| `AllyEffect` | 範囲内の自身以外の味方に与えるバフ |
| `Tile` | 設置するマスの種類 |
| `ClearDebuffs` / `ClearBuffs` | 対象のデバフ／バフを解除 |
| `Description` | UI向けの補足説明。文字列を書くだけでは特殊効果は実装されない |
| `OncePerTurn` | キャラごと・技ごとの1ターン1回制限 |

`ally` でも自分を対象にするには `Pattern` に `{0,0}` が必要です。
逆に、自分を除外したい技では原点を含めないか、効果側で明示的に除外します。
`AllyEffect` は現在、自分を除外する処理になっています。

回復技は仕様書の「ダメージ0」と「HP40回復」を、実装では `Power: -40` にまとめます。
この符号はAPIの `power` とフロントの回復表示にも使われます。

### 4.1 範囲と回転

右向きを基準に、前方がXの正方向です。盤面のYは上方向に増えます。
上下対称でない範囲では、仕様書の上側のマスがYの正方向になることに注意してください。

```go
adjacent                                      // 前方1マス
p(Position{0, 0})                             // 自身だけ
p(Position{1, 0}, Position{2, 0})              // 前方1・2マス
p(Position{1, -1}, Position{1, 0}, Position{1, 1}) // 前方1列の3マス
```

`attackCells()` は方向ベクトル `(dx, dy)` に対して次の回転を行い、盤面外のマスを除外します。

```text
rotatedX = offsetX * dx - offsetY * dy
rotatedY = offsetX * dy + offsetY * dx
```

フロントの `page.tsx` も同じ回転で対象マスを表示します。
方向の初期値は1Pが右向き、2Pが左向きです。
実際の攻撃対象は `Range` の数値内すべてではなく、回転後の `Pattern` に含まれるマスです。
クリックしたマスは範囲内であることの確認に使われ、通常の範囲攻撃は範囲内の全対象に作用します。

## 5. 共通処理で足りる技と、特殊処理が必要な技

通常攻撃、回復、既存のデバフ付与、バフ解除、デバフ解除は多くの場合定義だけで追加できます。
対象限定の追加ダメージ、別状態への切り替え、予約効果、移動を伴う技などはエンジン側の処理が必要です。

`ApplyAttack()` を変更する際は、次の点を確認します。

1. 認証・手番・リビジョン・キャラ生存・麻痺・コストの検証を通す。
2. コスト不足や不正対象の場合、HP・状態異常・使用回数を変更しない。
3. 敵味方、自身、拠点、設置マスをそれぞれ適切に処理する。
4. 効果が成立した後にコスト消費と使用済み記録を行う。
5. 戦闘ログを記録し、復活と勝敗判定まで実行する。

既存の直接攻撃には、通常のキャラ対象に加えて拠点・不変マスへの処理があります。
新しい特殊技がこれらにも作用するべきかを確認してください。
「敵キャラがいなくても設置マスだけを除去できる」といった技では、フロントの `validTarget` も対応が必要です。

### 5.1 自身対象の技と1ターン1回制限

現在、カスイマの「酒」、睡魔の「:star_struck:」「一旦寝るか」は `init()` で `OncePerTurn` を有効にしています。
新しい技で使う場合、定義作成時に `a.OncePerTurn = true` としても構いません。

- サーバーは `Character.UsedSkills[技名]` に使用した `State.Turn` を保存する。
- 同じターンに再実行すると拒否する。次の自分のターンはTurn値が変わるため使用可能。
- 履歴は試合JSONに含まれ、再読み込みで回数制限が消えない。
- フロントは「使用済み」と表示し、技ボタンを無効化する。
- `OncePerTurn` が有効でPatternが原点1マスだけの技は、技ボタンから直接実行する。
- `act(active.position, "attack", index)` と攻撃番号を明示的に渡す。`setAttackIndex()` の直後に更新後の値を読もうとしない。

同一キャラに同名の制限付き技を複数作ると履歴を共有します。必要なら専用の技IDを設計してください。
また、技名の変更は保存済み試合の使用履歴キーにも影響します。

## 6. パッシブの実装

### 6.1 共通数値パッシブ

`PassiveValues` と `passiveValues` は攻撃加算、ダメージ軽減、全快時加算、ターン終了回復、
他キャラのパッシブ効果値上昇、追撃確率などを保持します。
実際の適用箇所は `attackPower()`、`damageReduction()`、`passiveBoost()`、`processTurnEnd()` などです。

新しいフィールドを構造体に追加するだけでは動きません。参照する処理と説明文の両方を追加します。
ジーナの効果値上昇との組み合わせや、自分を範囲に含むかも確認してください。

### 6.2 発動時点に依存するパッシブ

| 既存例 | 主な実装箇所 | 注意 |
| --- | --- | --- |
| ソフィーの開始時バフ | `applyStartPassives()` | 待機試合の生成時ではなく、両者準備完了後にも正しく発動させる |
| ソフィーの離脱時デバフ | `checkWinner()` / `DepartureUsed` | 勝敗判定のたびに繰り返さない |
| ウェルブルスの輪廻転生 | `checkWinner()` / `ReviveUsed` | 勝敗確定前に全バフ・デバフ解除と復活。一度だけ |
| ナディアの追撃 | `ApplyAttack()` | 命中した敵ごとに判定。追撃からの連鎖は現在行わない |
| ダーナ・カスイマの耐性 | `addEffect()` | ダーナはデバフ拒否、カスイマは酒以外のバフ拒否 |
| 月葉のマス無効 | `triggerTile()`、移動判定等 | 通常の状態異常耐性とは別 |

HPが0になる経路は攻撃だけではありません。毒・地雷・押し戻し先のマスなども含めて検証します。
ウェルブルスの復活HPは基礎50に既存のパッシブ効果値補正を加える処理です。

## 7. ターンをまたぐ状態

`Character` の状態はJSONとしてDBに保存します。ブラウザー内だけの変数にしないでください。
Goに公開用フィールドを追加したら、必要に応じてフロントの `Fighter` 型も更新します。

| フィールド | 現在の用途 |
| --- | --- |
| `Effects` | 現在付与されているバフ・デバフ |
| `UsedSkills` | 各技を使用したターン番号 |
| `Wriggling` | 睡魔のくねくね状態 |
| `TemporaryBuffs` | 睡魔の技で新規付与され、ターン終了時に消すバフ |
| `DrankTurn` | カスイマの酒を使用したターン |
| `HangoverTurn` | 二日酔いを付与する予約ターン |
| `ReviveUsed` / `DepartureUsed` | 一度だけ発動するパッシブの消費状態 |

### 7.1 睡魔の技切り替え

1. `Definitions` に活動状態の `Attacks` と、くねくね状態の `AlternateAttacks` を登録する。
2. `processTurnEnd()` が自身の手番終了時に `Wriggling` を反転する。
3. サーバーの `actor()` が状態に応じた技配列を返す。
4. フロントの `definitionForFighter()` が同じ状態に応じて表示用の技を選ぶ。
5. 現在の状態欄とキャラカードにも状態を表示する。

`AlternateAttacks` は任意状態の汎用ステートマシンではありません。
3状態以上のキャラや別条件で切り替えるキャラは、状態フィールドと両側の分岐を追加設計します。

### 7.2 カスイマの酒・二日酔い

酒の威力上昇は自分の手番終了時に消え、`HangoverTurn = Turn + 2` で次の自分の手番への付与を予約します。
`completeTurnChange()` が二日酔いを付与し、次の自分の手番終了処理で解除します。
酒だけはカスイマのバフ拒否を通さずに自身へ付与しています。

### 7.3 新しい状態異常の追加

`addEffect()` の付与・耐性だけでなく、次も確認してください。

- `clearDebuffs()` / `clearBuffs()` の解除対象分類。
- `attackPower()`、`ApplyMove()`、`ApplyAttack()` の数値補正。
- `processTurnEnd()` や `completeTurnChange()` での継続ダメージ・期限処理。
- `lib/game.ts` の `EFFECT_DESCRIPTIONS`。
- 復活・解除・ターン切り替え後に効果や予約状態が残るか。

確率は `roll()` で判定します。現在は試合ID・リビジョン・対象等を使った決定的なハッシュ判定です。
同じ入力の結果を再現できますが、率の検証は複数の試合ID・リビジョンで行ってください。

## 8. 設置マス・押し戻し

設置技は `Target: "cell"` と `Tile` を指定します。
設置可否は `ApplyAttack()`、配置は `setTile()`、着地効果は `triggerTile()` が担当します。
現在、既存の設置マスは上書きできません。侵入不能マス・拠点への設置も拒否します。
不変マスにはHP、自然減少、攻撃による破壊、足元への設置という個別処理があります。

Reverseは命中した生存中の敵を `pushBack()` に渡します。
方向は対象の向きではなく攻撃方向です。2マス先、1マス先の順に移動可能な到着位置を探します。
到着位置では盤外・侵入不能マス・不変マス・他キャラ・敵拠点を確認し、移動できたらマス効果を発動します。
現在は到着位置を検証する実装で、2マス移動の途中のマスを歩行経路として検証する処理ではありません。

範囲内に複数の押し戻し対象がいる場合は、対象を処理する順番で空きマスが変わる可能性もテストしてください。

## 9. 画像とフロントへの反映

画像を次の場所に配置し、Go定義のファイル名と一致させます。

```text
Auxilia-web/public/characters/example.png
Auxilia-web/public/characters-mini/example_mini.png
```

Linux上では大文字・小文字を区別します。`Example.png` と `example.png` を混同しないでください。
立ち絵は `Portrait`、ミニ画像は `Image` です。

画像は `CharacterImage` を使います。ミニ画像では `mini` を指定します。
読み込み失敗時はそれぞれ `unknown.png`、`unknown_mini.png` に切り替わります。
パスには `NEXT_PUBLIC_BASE_PATH` が付くので、直書きURLでこの処理を迂回しないでください。

新技では次の表示も確認します。

- 編成画面の技名、パッシブ説明、HP・移動コスト。
- 戦闘詳細の対象・範囲・回復量・追加効果・Description。
- 戦闘盤面でクリックできる対象。
- 自身対象技の直接発動と使用済み表示。
- 特殊状態や残り回数など、ユーザーが判断に必要とする情報。

## 10. 使用率集計と保存への影響

キャラクターIDは累計使用率と週間使用率にも使用されます。
通常対戦が開始したときに両編成が記録され、テストモードは除外されます。
週間用のキャラクター登録はサーバー起動時に `Definitions` から行われます。

新キャラのために集計へ固定列を追加する必要はありません。CSV列はIDから生成します。
一方、既存IDを変更すると過去の使用数とは別キャラになります。

基礎HPは試合生成時に `Character` へコピーされます。定義変更がすでに進行中の試合へ
すべて同じように反映されるとは限りません。検証時は新しく試合を作成してください。

## 11. テストと手動確認

### 自動テスト

サーバーのリポジトリで実行します。

```sh
go test ./...
```

代表的な既存テストは以下です。

| テスト | 用途 |
| --- | --- |
| `characters_test.go` | キャラ数、基本数値、技の定義。新キャラ追加時は期待値表も追加する |
| `character_actions_test.go` | 範囲、対象、追加効果の実戦処理 |
| `rules_alignment_test.go` | パッシブ・特殊処理の仕様照合 |
| `verbulus_test.go` | 復活、解除、不変マス |
| `kasuima_test.go` | 酒、二日酔い、押し戻しと着地 |
| `suima_test.go` | 状態切り替え、範囲外追加効果、解除 |
| `self_skill_test.go` | 自身技の効果、回数制限、失敗操作、再読み込み |

定義値の比較だけでは不十分です。次の動作から該当するものを検証します。

1. 四方向の範囲と盤端、範囲外の敵が巻き込まれないこと。
2. 自分・味方・敵・拠点・設置マスの区別。
3. 効果の開始、持続、解除、次ターンへの予約。
4. コスト不足・麻痺・使用済み・不正対象を拒否し、状態を変えないこと。
5. パッシブ補正、耐性、復活との組み合わせ。
6. JSON保存・復元後にも状態や消費回数が維持されること。
7. 通常対戦に加えて、テストモードでも両陣営から操作できること。

フロントのリポジトリではPages用ビルドを確認します。

```sh
npm run build:pages
```

型や画面ロジックを変更した場合は、対象プロジェクトのTypeScript・ESLintチェックも実行してください。
テストを実行できなかった場合は、コンパイル成功と動作検証成功を区別して報告します。

### テストモードでの確認

1. サーバーに `TESTMODE_PASSWORD` が設定されていることを確認する。
2. 新キャラを含む3体を編成する。
3. Tキーを押しながら「対戦開始」をクリックして認証する。
4. 両陣営を操作し、技・ターン切り替え・HP・状態異常を確認する。
5. 「終了」でエントランスに戻る。時間切れでも終了する。

両陣営は同じ編成ですが、HP・状態・技の使用履歴は独立しています。
テストモードの試合は使用数・使用率を増やしません。

## 12. 変更の共有とデプロイ

作業完了時は、基準にした仕様、変更した技・対象・期間、検証結果、未確定な解釈を報告します。
「説明を更新した」「処理を実装した」「テストした」を混同しないでください。

Go側の定義・処理はサーバーの再デプロイで反映されます。
画像・TypeScript型・画面判定を変更した場合はフロントも再デプロイします。
APIに新しいフィールドを追加した場合は、旧状態で未設定でも扱える型・初期値を意識してください。

最終確認事項：

- rulesの数値・範囲・対象・特殊効果に対応した。
- パッシブは説明だけでなく処理があり、対象からの自身除外も正しい。
- 選択一覧・画像・戦闘詳細・対象クリックに反映された。
- ターン限定効果と一度だけの効果を保存できる。
- 不正操作や失敗でコスト・回数だけを消費しない。
- 使用率集計を壊さず、IDの互換性を維持した。
- 必要なテストとビルドの結果を確認した。
